# 5. ORDER STATUS SYSTEM

Implement a clear, consistent order lifecycle.

Use an enum/constraint or equivalent controlled status model rather than arbitrary free-text status values.

At minimum support:

* `pending`
* `confirmed`
* `processing`
* `shipped`
* `delivered`
* `cancelled`

If the existing architecture already contains additional legitimate states, preserve them where appropriate instead of creating conflicting duplicates.

Define valid transitions and prevent nonsensical status changes.

Examples:

* pending → confirmed
* confirmed → processing
* processing → shipped
* shipped → delivered
* pending/confirmed/processing → cancelled where business rules permit

Prevent invalid transitions such as:

* delivered → pending
* cancelled → shipped
* cancelled → delivered

Do not allow arbitrary customer-controlled status updates.

# 8. INVENTORY / STOCK CONSISTENCY

This is a critical requirement.

Order creation and inventory changes must be safe against race conditions.

Prevent overselling when multiple customers attempt to purchase the same product simultaneously.

Inspect the existing stock architecture first.

Implement an atomic / transaction-safe inventory adjustment mechanism using the project's existing Supabase architecture.

Rules:

* Do not allow stock to become negative.
* Do not rely only on frontend checks.
* Server/database must enforce the actual safety.
* Order creation must verify inventory availability.
* Inventory changes must remain consistent with order state.

Define when stock is actually deducted based on the existing business flow.

Do NOT accidentally decrement stock twice.

Do NOT decrement stock again merely because an admin changes a status.

If cancellation requires stock restoration according to the existing business rules, implement it safely and exactly once.

Ensure repeated requests/retries cannot double-decrement or double-restore inventory.
