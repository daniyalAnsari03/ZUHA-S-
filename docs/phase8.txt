# 4. GUARDIAN ARCHITECTURE

Implement Guardians as a real security/control layer, NOT as a decorative AI chatbot.

A Guardian must be capable of evaluating AI-driven actions before execution.

Guardian responsibilities should include:

* identify requested action
* identify requesting agent/employee
* identify business/user context
* identify target resource
* check permissions
* check action policy
* validate arguments
* detect missing context
* reject unauthorized actions
* reject malformed actions
* require approval where appropriate
* allow safe actions
* record decision
* explain rejection where useful
* prevent unsafe background execution

The Guardian must sit between AI reasoning and privileged actions.

Do not rely on the AI model itself to enforce authorization.

Authorization must be enforced server-side.

---

# 5. GUARDIAN ACTION MODEL

Define a clear action model.

Each AI action should have enough context to establish:

* business_id
* user_id when applicable
* agent/employee identity
* action/tool name
* target resource
* requested arguments
* risk level
* permission requirement
* approval requirement
* timestamp
* decision
* reason
* execution status

Use typed structures where the project already uses TypeScript.

Do not use uncontrolled `any` objects for security-critical decisions.

---

# 6. GUARDIAN DECISIONS

Guardians should support decisions such as:

* ALLOW
* DENY
* REQUIRE_APPROVAL

Use the project's existing conventions if an equivalent system already exists.

Never let an AI-generated "approved" field bypass the actual Guardian.

The Guardian itself must calculate the final authorization decision.

---

# 7. ACTION RISK LEVELS

Establish sensible risk classification for AI actions.

Examples:

LOW RISK:

* reading business analytics
* reading products
* reading inventory
* generating text
* generating reports

MEDIUM RISK:

* creating drafts
* modifying non-critical business content
* preparing marketing content
* preparing customer communication

HIGH RISK:

* sending external messages
* modifying important business data
* changing orders
* changing inventory
* financial actions
* destructive actions
* actions affecting customers
* automated external communication

CRITICAL/RESTRICTED:

* credential/security changes
* destructive bulk operations
* sensitive data access
* irreversible financial operations

Do not allow risk classification to replace authorization.

Both permission and risk policy must be evaluated.

---

# 8. APPROVAL CONTROL

# 13. WEBHOOK SECURITY

Treat webhook input as untrusted.

Validate:

* HTTP method
* required fields
* payload structure
* expected event shape
* signature/authentication where supported
* configured business context
* sender/message identifiers

Do NOT trust:

* business_id supplied by the client
* user IDs inside arbitrary payloads
* AI-generated authorization
* message metadata without validation

Prevent cross-business message routing.

A WhatsApp event belonging to Business A must never be processed using Business B's data.

# 14. IDEMPOTENCY

A duplicate webhook must not:

* create duplicate orders
* trigger duplicate AI actions
* send duplicate responses
* create duplicate notifications
* execute duplicate automation

Design idempotency at the database/service layer where appropriate.
