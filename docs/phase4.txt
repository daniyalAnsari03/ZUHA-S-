# 2. DATABASE — CARTS

Create the required Supabase migration.

Create a secure cart system supporting authenticated customers.

Recommended structure:

### carts

* `id` UUID primary key
* `user_id` UUID NOT NULL
* `status` appropriate cart status
* `created_at`
* `updated_at`

Requirements:

* One active cart per user.
* Appropriate unique constraint/index.
* Proper foreign key to authenticated user/profile according to existing architecture.
* RLS mandatory.

# 3. DATABASE — CART ITEMS

Create:

### cart_items

* `id` UUID primary key
* `cart_id` UUID NOT NULL
* `product_id` UUID NOT NULL
* `quantity` integer NOT NULL
* `created_at`
* `updated_at`

Requirements:

* quantity must be greater than 0.
* Appropriate unique constraint for one product per cart.
* Foreign keys.
* Appropriate indexes.
* Prevent invalid product references.
* RLS mandatory.

Do NOT trust client-provided prices.

Prices must always come from the trusted product data/service layer.

# 4. DATABASE — WISHLIST

Create a proper wishlist foundation.

Recommended:

### wishlists

* `id` UUID primary key
* `user_id` UUID NOT NULL
* `created_at`
* `updated_at`

### wishlist_items

* `id` UUID primary key
* `wishlist_id` UUID NOT NULL
* `product_id` UUID NOT NULL

Requirements:

* One wishlist per user.
* A product cannot appear twice in the same wishlist.
* Proper foreign keys/indexes.
* RLS mandatory.
* Users can access only their own wishlist.

If the existing architecture supports a simpler user-to-product wishlist relation safely, reuse that approach instead of creating unnecessary tables.

# 5. RLS / SECURITY

Security is mandatory.

Customers must only be able to:

* read their own cart
* modify their own cart
* read their own wishlist
* modify their own wishlist

Users must NOT be able to:

* access another user's cart
* access another user's wishlist
* change another user's cart items
* change another user's wishlist
* submit arbitrary prices
* manipulate product ownership
* bypass stock validation
* bypass authentication

Public users may browse products but must not modify customer cart/wishlist records.

Never expose:

* service-role key
* private credentials
* database secrets

Do not disable RLS.

# 13. PAYMENT ARCHITECTURE

Phase 4 must establish the checkout payment architecture without locking the project to an unsafe implementation.

The system should support a payment-provider abstraction suitable for Pakistan.

Do NOT hard-code a single payment provider if the existing architecture is designed for multiple providers.

Payment amount must always be calculated server-side from trusted product/cart data.

Never accept a client-submitted total as authoritative.

Do NOT expose payment secrets.

Do NOT implement fake payment success.

If a payment provider is not yet configured, create a clean provider interface and a safe unavailable/configuration state rather than pretending payment succeeded.

---

# 14. CHECKOUT VALIDATION

Before checkout submission, server-side validation MUST verify:

1. User is authenticated.
2. Cart exists.
3. Cart belongs to current user.
4. Cart is not empty.
5. Every product still exists.
6. Every product is active.
7. Current prices are retrieved from trusted DB data.
8. Stock is still sufficient.
9. Quantities are valid.
10. Final subtotal/total is calculated server-side.
11. Customer/shipping information passes validation.

Never use stale client prices.

# 16. STOCK / CONCURRENCY SAFETY

Cart operations must account for concurrent stock changes.

Do not assume:

`current stock → client quantity → checkout`

is safe.

At checkout, revalidate stock from the trusted database.

Where appropriate, use an atomic database operation/transaction/RPC for inventory-sensitive operations.

Do not allow negative stock.

Do not silently oversell.

If stock becomes unavailable, show a clear error and prevent checkout.
