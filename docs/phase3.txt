## PHASE 3 GOAL

Replace the current mock/read-only storefront product data with a proper database-backed product and category system using Supabase.

The storefront should ultimately read products/categories from the real database while preserving the existing premium UI.

---

# 1. DATABASE — CATEGORIES

Create a proper `categories` table through a Supabase migration.

Recommended fields:

* `id` UUID primary key
* `name` text NOT NULL
* `slug` text UNIQUE NOT NULL
* `description` text nullable
* `image_url` text nullable
* `is_active` boolean NOT NULL DEFAULT true
* `sort_order` integer NOT NULL DEFAULT 0
* `created_at`
* `updated_at`

Requirements:

* Appropriate constraints.
* Appropriate indexes.
* `updated_at` should update correctly.
* Slugs must be unique.
* Use UUIDs.
* No unnecessary fields.

# 2. DATABASE — PRODUCTS

Create/upgrade the proper `products` table through migration.

Products must support the existing storefront and future commerce phases.

Fields should include at minimum:

* `id` UUID primary key
* `category_id` UUID nullable/appropriate FK to categories
* `name`
* `slug` UNIQUE
* `description`
* `fabric` or equivalent product-detail field
* `price`
* `compare_at_price` nullable
* `sku` nullable/unique where appropriate
* `stock_quantity`
* `low_stock_threshold`
* `image_url`
* `is_active`
* `is_featured`
* `sort_order`
* `created_at`
* `updated_at`

Use appropriate PostgreSQL types and constraints.

Price must be stored safely as numeric/decimal, NOT floating-point.

Do not duplicate category text when a proper category relation can be used.

# 3. SUPABASE RLS / SECURITY

RLS is mandatory.

Design policies carefully so that:

* Public storefront can read only products/categories that are intended to be publicly visible.
* Inactive products/categories are not exposed publicly.
* Admin/authorized users can manage products/categories according to the existing auth/role architecture.
* Users cannot modify another business/owner's data if the existing architecture is multi-tenant.
* Never expose service-role credentials to the browser.
* Do not bypass RLS from frontend code.
* Do not give arbitrary database access to AI.

Follow the existing project's security architecture and `AGENTS.md`.
